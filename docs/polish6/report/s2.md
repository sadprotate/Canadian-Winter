# §2 — The Godot errors after pulling

**Reproduced exactly.** In a CRLF scratch clone (like the owner's GitHub Desktop checkout), the steps
are: import `15be65a`, check out `1b38f4a` keeping `.godot/`, open it again. That prints the owner's
three errors (`icons.gd:125 ToolIcons`, `icons.gd:140 Equipment`, "Failed to load script"). It does
so headless and windowed, with this PC's console build and with the owner's own mono build. The
cause is the class cache. The editor compiles `icons.gd` at start-up, before its first scan, while
the global class list is still the old `.godot/`'s, which has none of round 5's classes.

**Fixed by referring to round 5's classes by path.** Every script that existed before round 5 now
does it through preload constants: 21 scripts. So do the 4 round-5 scripts those preloads pull in.
Hardening only the 21 made the upgrade import worse (16 error lines), so the 4 were needed too.
After the fix, the same upgrade import is clean in all three builds and modes.

**CI gets an upgrade-import step.** It fails on the pre-hardening tree and passes on this one, run
locally in six scenarios.

## The reproduction

**Setup.** A clone of the repo in the scratchpad (`s2/up`), never the main checkout. Git's system
config has `core.autocrlf=true` and the repo has no `.gitattributes`, so every text file is checked
out CRLF, as in GitHub Desktop. Godot 4.7.2 ran one process at a time through the wrapper.

The errors in the log (this PC's console):

   at: GDScript::reload (res://scripts/ui/icons.gd:125)

These are the owner's lines. The editor's Output panel prints the same errors as
`ERROR: res://scripts/ui/icons.gd:125 - Parse Error: …`.

**Diagnosis (confirmed).**
- At start-up the editor reads the global class list from `.godot/global_script_class_cache.cfg`.
  After a pull that list is the old one.
- Before the first file-system scan, something in the editor's start-up asks for a type named
  `Icons`. Run 7 shows that the trigger is the class *name*, not a restored tab or the main scene.
  `ScriptServer` resolves it to the project's `Icons` and compiles `icons.gd`. `ToolIcons` and
  `Equipment` aren't in the old list, so the compile fails.
- The scan then registers the new classes, and everything after it is fine: run 4 and runs 3 and 5
  are clean.
- CI never hits this because its import has no `.godot/`, so the list is built from the tree.
- Only `icons.gd` errors because it's the only script compiled before the scan. That's also why
  the owner saw no other errors.
- Deleting `.godot/` works because the editor then builds the class list from the files.

**Not tested:** Godot left open *during* the pull. The editor rescans only when its window gets
focus again, which can't be done unattended without driving the desktop. The class-cache diagnosis
and the hardening cover that case too, because no script now needs the old list to know a round-5
class.

## The other explanations

- **Line endings (CRLF).** There's no `.gitattributes`, and `core.autocrlf=true` comes from Git's
  system config (`C:/Program Files/Git/etc/gitconfig`), so `.gd`, `.tscn`, `.cfg` and `.import`
  files are CRLF on disk. The index is LF, except for one doc,
  `docs/polish5/POLISH_ROUND_5_PROMPT.md`.
  - **CRLF doesn't cause the errors:** the LF clone (run 10) prints the same three. The GDScript
    parser reads CRLF fine: §0's whole baseline ran on this CRLF checkout, 209 tests passed.
  - What CRLF does do: Godot writes every `.import` file with LF, so a fresh CRLF checkout shows
    all 74 `.import` files as modified after the first import (in an LF clone: none).
  - That is the `icon.svg.import` item in STATUS: `git diff` is empty, and staging them records no
    change (checked in the scratch clone: `git add` of the 74 → `git diff --cached` empty).
- **Mono-only.** The non-mono console build reproduces it (runs 2, 8). The owner's mono build
  (run 9) prints the identical three lines and, hardened, nothing. The project has no C#; both
  builds run the same GDScript module.
- **A missing `.uid`.** At `1b38f4a` and at HEAD every `.gd` has its `.uid` committed (90 and 92;
  no orphan `.uid`, no duplicate uid).
  - At `15be65a`, five scripts had none: `scripts/world/computer_screen.gd`,
    `scripts/world/framed_photo.gd`, `tests/indicator_report.gd`, `tests/test_polish4.gd` and
    `tests/weather_truth.gd`.
  - The `15be65a` import generates random uids for them (untracked files), and `1b38f4a` commits
    different ones. So a pull into such a checkout first stops with "untracked working tree files
    would be overwritten".
  - Once they were moved aside, the stale uid cache (the old random uids) printed no error or
    warning (run 2).
  - So it's not the cause, and it can't recur for these scripts. `CLAUDE.md` already makes every
    new script's `.uid` part of its commit.

## The hardening

**The rule applied:** a reference to one of round 5's nine classes
(`AddressSigns`, `Buildings`, `Equipment`, `HeatedPad`, `Heating`, `ItemUpgrades`, `SidewalkCrew`,
`SpeedControl`, `ToolIcons`) goes through `const _<Class> := preload("<its path>")` instead of the
global name. Each script that does this has the constants in one block before its first member,
under a two-line comment:

```gdscript
# Polish 6 §2: classes added in polish 5, by path rather than global name, so this script still
# loads when the editor's class cache predates a pull.
const _Equipment := preload("res://scripts/data/equipment.gd")
```

**How the list was found.**
- With grep: every `.gd` in both `15be65a` and HEAD (76) was searched for the nine names as whole
  words.
- A small tokenizer (scratch `s2/harden.py`) kept only code: comments, strings and the
  `class_name` line were left out. That is how "Heating pouches", `@export_group("Equipment")`,
  `"Equipment store"`, `name = "HeatedPad"` and the comments stay as they were.
- It made the replacement too, and I checked every changed line by eye.
- No `.tscn` / `.tres` holds an embedded script or names these classes.
- Round 5 moved and removed no class. The nine are the only additions to the cache.

## The CI step

`.github/workflows/ci.yml`, a new step **"Upgrade import (base commit's .godot/, then this
commit)"** after *Test suite*. The job and every existing step are unchanged, and so is the job
name (a required check keeps its name). The header comment mentions the new step.

1. **The base.**
   - The base is `github.event.pull_request.base.sha` on a PR, and `github.event.before` on a push
     to `main`.
   - When there is neither (`workflow_dispatch`, or the all-zero SHA of a new ref), it falls back
     to `HEAD^`, after `git fetch --depth=2`. With no base at all, it prints a `::notice::` and
     skips.
   - The base is fetched by SHA (`--depth=1`) unless it's already there. If it can't be fetched
     (say, after a force-push), the step prints a `::warning::` and skips. It doesn't fail.
2. **Its own folder.** A `git worktree` in `$RUNNER_TEMP/upgrade` at the base, so the suite's
   checkout and `.godot/` are untouched. Running after the suite also keeps the suite's `user://`
   as it was.
3. **Import the base** (`--editor --quit`, log `logs/upgrade_base_import.log`). Errors there belong
   to the base and give a `::warning::` only.
4. **This commit over it:** `git -C <dir> checkout --force --detach <HEAD>`. `.godot/` is ignored,
   so it stays. `--force` overwrites what the base import generated, for example a `.uid` this
   commit adds (the `15be65a` case above). `HEAD` is the PR's merge commit, which is what `main`
   becomes.
5. **The upgrade import**, logged in `logs/upgrade_import.log`. It fails on any line matching the
   clean import's pattern (`ERROR|SCRIPT ERROR|Failed loading resource|Cannot open file`), with an
   `::error::` that names the fix (a preload constant, CLAUDE.md).
6. **The main scene for a few seconds:**
   `godot --headless --fixed-fps 60 --path <dir> res://tests/run_log.tscn -- --play=5`, logged in
   `logs/upgrade_run.log`. It runs the real main scene: menu → New Game → 5 s of play → sleep →
   menu → Exit.
   - It quits the game's own way (`AudioMgr.quit`), so the engine's exit noise doesn't appear.
     (`--quit-after` instead would quit with the menu music still playing. That is HANDOFF §13
     item 13's `ERROR: N resources still in use at exit`, which matches `ERROR`.)
   - If that one line ever shows up, it's a `::warning::`, not an upgrade error. Every other error
     line fails the step, and so does a non-zero exit (`run_log` exits 2 when a step never
     completes).
7. All three logs go up with the existing *Upload logs* step (`logs/`).

**Validation here.**
- **YAML:** PyYAML, Ruby, Node and Perl's YAML modules aren't on this PC. So a strict
  standard-library parser for the subset the workflow uses (scratch `s2/yamlcheck.py`) parsed the
  file to JSON and checked it:
  - It checks the shape: top-level keys, job keys, each step's keys and exactly one of
    `run` / `uses`, balanced `${{ }}`.
  - The old file and the new one both parse, with 8 → 9 steps in the right order.
  - Seven broken copies were all caught: a `run:` line dedented (two places), a tab, `if: !cancelled()`
    without `${{ }}`, a duplicate `env` key, an unbalanced `${{`, an unknown step key.
- `bash -n` on the extracted `run:` block passes.
- **Logic:** the parser wrote out the step's `run:` block exactly as GitHub gets it, and it was run
  with `bash --noprofile --norc -eo pipefail` (GitHub's default shell).
  - It ran in a scratch clone (`s2/ci`), CRLF like the owner's.
  - `RUNNER_TEMP` was scratch, and `APPDATA` was scratch so `run_log` never touched the owner's
    saves.
  - `godot` was the wrapper.

## Line endings: the STATUS item, decided

**No `.gitattributes`, and `icon.svg.import` stays uncommitted.** It isn't a change: staging the
74 LF-rewritten `.import` files records nothing.
- The line endings aren't the cause (above). The brief lists no line-ending change.
- A `.gitattributes` would change how every text file is checked out on the owner's PC.
  `text=auto` would also flag the one CRLF-committed doc until it's renormalized (whole-file
  churn).
- The cost of leaving it: GitHub Desktop lists `.import` files as changed, with no visible change,
  after an import that rewrites them. That only matters if a pull changes the same file; then
  discarding them first is enough.
- If the owner wants the list quiet, one line (`*.import text eol=lf`) would do it. That's the
  owner's call; it goes in STATUS as an open item.

## For the PR description (the user note)

> **If Godot shows errors after a pull** (for example *Identifier "ToolIcons" not declared in the
> current scope* in `icons.gd`):
>
> 1. Close Godot.
> 2. Delete the project's `.godot` folder: it's inside the project folder, next to
>    `project.godot`. Windows may hide it, so turn on *View → Hidden items* in File Explorer.
>    GitHub Desktop doesn't list it, and it isn't part of the repository.
> 3. Open the project again. The first import takes a minute.
>
> Better: **close Godot before you pull**, and open it after.
>
> The errors came from Godot's list of the project's classes in `.godot`, which was still the one
> from before the pull. They showed once, the first time the editor opened. The scripts from this
> round no longer depend on that list, and CI now tests an upgrade like yours, so it shouldn't
> happen again.
>
> GitHub Desktop may list `.import` files as changed when nothing in them changed (only their line
> endings). You can leave them or discard them.
