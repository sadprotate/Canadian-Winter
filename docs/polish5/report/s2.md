## 2.1 Keys

| Action | Before | After | Context |
|---|---|---|---|
| `drop` ("Drop tool") | Q | **G** | foot |
| `store` ("Put on the rack") | — | **F** (new) | foot |
| `use_pouch` | G | **H** | foot |
| `interact` | E | E | global |

- **H was free.** H is also `veh_horn`, but that is a vehicle action and the pouch is a foot
  action: the existing rule (`rebind()`: conflict only within a context or with a global action)
  lets them share it, like W for walking and driving; the pouch is only read on foot. So no
  "nearest free key" was needed. Q is now unbound.
- **`store`** is in `ACTIONS` (so it can be rebound, shows in Settings → Controls and in the Help
  app's binding list, and takes part in the conflict check and the cap) but nothing reads it: no
  prompt, hint or message, F does nothing. Reading taken: "shows nothing" = nothing in the game
  world; the binding tables list every action. Note for §15: a `tool_rack` upgrade already exists
  (a wall rack beside the garage, E to hang / take, 8 tools, `game_root.build_tool_rack`).
- **Conflict check in every place** — `Settings.live_actions(place)` / `Settings.conflicts(place)`:
  - foot = foot + global actions; vehicle = vehicle + global;
  - machine (walk-behind blower) = the four moves, LMB, slots 1–4, the chute keys Z / C, + global
    (read from the code: jump, sprint, crouch, the wheel and the tool keys do nothing there);
  - computer, menu = Pause only (the player is frozen / the tree paused; the rest is UI).

  Result with the new defaults: no conflict in any of the five; nothing moved. In the game (real
  key events): at the computer G, F, H, E, R, 2, M and V change nothing; in the pause menu G, F, H,
  E change nothing; in the truck H is the horn (no pouch used), G and F drop nothing, E gets out.
- **Gap found, not changed:** `rebind()` knows only foot / vehicle / global, so a player can bind a
  foot action that is live at a walk-behind machine (a move, LMB, slots 1–4) to Z or C and get both
  there. The defaults are clear of it; changing what players may bind was left alone.

### Settings migration (`user://settings.cfg`)

- `[meta] controls_version` (absent = 1; now `Settings.CONTROLS_VERSION` = 2), written on every save.
- `Settings.OLD_DEFAULTS[1] = {drop: Q, use_pouch: G}`. `Settings.controls_from(cfg)` (static,
  testable): every stored binding is read; each action still at its old default moves to the new
  one if no action it shares a context with holds that key — repeated until nothing moves, so
  use_pouch leaves G before drop takes it, in any order. A binding the player set is never moved.
  If a move would collide with one, the moved action keeps its old key (and a chain follows: jump
  on H keeps use_pouch on G, which keeps drop on Q).
- A new action whose default key is held by a stored binding in a shared context starts
  **unbound** ("—"); from version 2 an unbound action (`[]`) is saved and stays unbound (before,
  `[]` fell back to the default, which would have re-created the clash).
- `Settings.load_controls()` (called from `_ready`) migrates and writes the file back at once;
  a fresh install writes nothing until something changes; a version-2 file is never migrated
  again (Q chosen after the move stays Q). Reset to defaults gives the new defaults.
- **For §9:** adding the fast-forward action needs nothing here (it gets its default unless a
  stored binding in a shared context holds it). If a *default changes*, bump `CONTROLS_VERSION`
  and add `OLD_DEFAULTS[2]`.

## 2.3 Action rate limit — measured first

`tests/click_bench.tscn` (new; extends grind_bench, same start: Fun, seed 2024, Dec 1 9:00, clock
stopped, the player's path box, bare hands). Presses are real key / mouse events for the current
binding, half of each period held. The clicking bot stands in the path facing the lawn, looks
down at the snow by its feet (scoop there, the release tosses it onto the lawn), turns to the other
side / wades on when the snow at its aim is gone, and doesn't click while it moves (its best case).
"Removed" = snow gone from the box per second once everything thrown has landed. 30 s per run.

| Run | before (no cap) | after (cap 6/s) |
|---|---|---|
| LMB hold + sweep (the grind_bench bot) | 0.0413 m³/s | 0.0413 |
| LMB hold in place, release when full | 0.0290 | 0.0290 |
| LMB auto-click 5/s | 0.0599 (123 of 123 registered) | 0.0599 (123 of 123) |
| LMB auto-click 10/s | 0.1036 (210 / 210) | 0.0756 (149 / 229) |
| LMB auto-click 20/s | **0.1471** (304 / 348) | 0.0782 (160 / 458) |
| LMB auto-click 50/s | 0.0983 (212 / 1056 ¹) | 0.0768 (154 / 1143) |
| RMB hold / auto-click 5–50/s, walking up the path | 0.0066 m³/s pushed for all; 50/s: 10.1 presses/s | 0.0066 for all; 6.0 presses/s |
| E × 100 at a shovel on the ground, 5–50/s | picked up once, tools 2 → 2 | same |
| G × 100 with a shovel in hand, 5–50/s | dropped once, 2 → 2 | same |
| E + G alternating × 100 each, 50/s, events batched as at 20 fps ² | **2 → 6 tools** (+ 74 engine errors) | 2 → 2 (and 2 → 2 with the cap off) |

¹ At 50/s most presses go down and up inside one frame and the polled scoop never sees them.
² `--fps=20`: three frames' presses reach the engine together, as on a slow frame.

What a burst does that a human can't:
- **An extra bite per press — the cap doesn't remove it.** Each press opens a stroke, and a stroke
  opens with an in-place bite: `_fill` resets the dig cycle (`_dig_timer = 0`) and the re-cut memory
  at the start of every stroke, so the first frame digs `fill_rate × cycle_time × 0.4` (17 L for
  bare hands, half their 30 L capacity) where sweeping takes 1.4 L per frame. Measured: 14–15 L per
  registered press at every rate. A human tapping at 5/s already gets it (0.060 m³/s = 1.45× hold +
  sweep). The cap takes 20/s from 3.6× hold + sweep down to ~1.9× (and every rate to the cap rate's
  level), but no cap of 5 or more brings clicking under sweeping; that would take ~3/s, which
  breaks tapping at 5/s. Removing the gain means changing how a stroke starts its cut, which §2
  rules out. Experiment (reverted, `click_experiment_digtimer.log`): letting the dig cycle run on
  across presses drops clicking to 0.018–0.027 m³/s (below sweeping), but grind_bench's hold-and-
  sweep bot loses too (0.0376 → 0.0349 m³/s, box 3.2 → 3.7 min): its quick strokes lose the opening
  bite as well. So it's a scoop-design decision for whoever owns the scoop.
- **A throw per release** — one per registered press (tested); an ignored press doesn't throw.
- **RMB** — no per-press gain (pushing works per frame while held).
- **A duplicated item — found and fixed.** Two E presses in one frame on a tool lying on the
  ground both picked it up: `ToolItem.interact` ran again before its `queue_free()` took effect.
  Fixed twice over: the cap passes at most one press per action per physics frame, and
  `ToolItem.interact` returns when the item is already queued for deletion (also covers crates:
  pouches and upgrades). No item was lost in any run.
- **Errors on dropping a carried item (baseline bug on the drop path).** With the four slots full
  and a fifth tool carried, dropping it in first person logged two engine errors every time
  (`Basis … must be normalized`, `fp_arms.gd:111`): for one frame the hands were posed on the grip
  of the "__carry__" item (a zero-length shaft). Reproduced on the baseline build
  (`probe_carry_drop.gd`). The tool controller now switches to what's left in your hands in the
  frame of the drop (`_sync_tool()` after `drop_tool()`); behaviour otherwise unchanged.

### The cap

- `Settings.accept_press(action)`: at most `Catalog.balance.input_max_presses_per_s` (new balance
  value, **6.0**; 0 = off) accepted presses per action in any one second, and at most one per
  physics frame. Time is the physics-frame count (`Engine.get_physics_frames()`, window =
  `physics_ticks_per_second`), so it holds under `--fixed-fps` and at any frame rate. A rejected
  press is ignored, never queued. Readings: a sliding one-second window rather than a minimum gap
  of 1/6 s, so a human's uneven taps at 5/s never lose one; one per frame so a burst in a slow
  frame can't pass several.
- Limited (`Settings.RATE_LIMITED`): `primary` (hands and shovel-type tools, the electric shovel,
  walk-behind blowers), `secondary`, `interact`, `drop`, `store`, `use_pouch`, `tool_angle`,
  `veh_tool`. Callers ask once, on the press edge, and act for as long as the button is held
  (`ToolController._held()`, the primary edge in `_shovel_type`, the walk-behind run edge), so
  holding is never cut short. A press over the cap: no scoop and no throw on its release; no push;
  no pickup / drop / pouch / blade change.
- Not limited: UI clicks (computer, menus, settings, dialogs), F1, Pause, map, Tab, camera, slots
  and wheel, movement, jump, horn, radio, and E moving Gerry's dialogue on (his lines, not a world
  change).

## 2.4 Readings taken

- The brief's test "auto-clicking at 20 and 50 per second removes no more snow per second than the
  sweeping bot, within noise" can't hold together with "don't change how a scoop cuts" and
  "tapping at 5/s works normally" (2.3). The test asserts what the cap guarantees: at 20 and 50/s no
  more presses register than the cap, no more snow comes off than clicking at the cap rate (within
  12 %), one throw per registered press, and without the cap 20/s removes ≥ 1.4× as much (so the
  check fails if the cap stops working). The hold-and-sweep rate and the ratios are printed
  (last run: sweep 0.0407; cap rate 0.0713; 20/s 0.0706 = ×1.73 sweep; 50/s 0.0746 = ×1.83; no cap
  20/s 0.1422).
- `store` listed in Settings and the Help app's binding list (2.1).
- "Within noise" for grind_bench: identical numbers.
