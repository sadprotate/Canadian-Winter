## 7.1 What changed

**Order, ids, renames.** `ComputerUI.APP_IDS` (stable ids: `weather`, `contracts`, `board`, `store`,
`upgrades`, `bills`, `orders`, `property`, `help`) beside `APPS` (the names shown) and
`app_index(id)`; every reader (the monitor, tests, `shot.gd`) goes through the ids, so §16 inserts
`Real estate` after Orders by adding one id and one name. Renamed: "Active Contracts" → "Contracts"
(it now holds Active and History); "Contract Board", "Equipment Store", "Bills & Payments",
"Property & Storage" → the brief's sentence case ("Contract board", "Equipment store", …). No app was
split and none removed.

**One layout** (1640 × 900 window as before, centred on every canvas):
- header — the company's name (or "Your company", muted, until it has one), "Reputation N", the
  battery line during an outage, money, "Fri Dec 3  11:03", Close (key from the input map);
- sidebar — the nine apps, the selected one in orange, the last action's message under them;
- content — the app's title (30 px), then its content in a vertical scroll area.
- Type scale for every app: title 30, section 22, card line 22, text and table cells 18, notes 16;
  12 px between blocks, 28 px between table columns. Tables are `GridContainer`s, so columns line
  up: pending bids, history, bills, transactions, orders, property, alerts, controls, box progress.
- Store and upgrade cards keep a fixed-width price column: the Buy button is always "Buy" (disabled
  when it can't be bought) and the reason ("Not enough money.", "Requires …") is a wrapped line under
  it, with "Owned" as before. Before, the reason replaced the button text and widened the column card
  by card.

**Less text** (functions unchanged): the board's two-sentence intro → one line; the listing terms
lost "one real hour = one game day" (wrong after §9) and were shortened; the store and upgrade
notes, the bill rule, the property note and the weather note are one short line each; the city
grader line is "Next pass: … · Passes this winter: N" (the "every 3–4 days" sentence would be wrong
after §11); "Vehicles (permanent equipment)" → "Vehicles". Help keeps Gerry's lines as they are
(HelpText is shared and §9 rewrites its rates).

**Weather** keeps its data source (`Weather.forecast` / `forecast_text`, the pass-4 model); §8 makes
the TV and this app share one forecast — not started here.

**Contracts.** Header row: the name, "Reputation N", Rename. Tabs "Active (n)" / "History (n)".
- Active: the contracts running (in progress, needs clearing, clear — waiting for snow): address,
  kind, status, pay (/ visit), client and visits, the time left (today's 48-hour clock: §10 turns it
  into a due time), each box with its bar and %. Completed and lost contracts are no longer listed
  here (they were before, lost ones for 14 days): they are in History.
- History: newest first, grouped by winter, columns Date · Address · Job (One-time job / Visit ·
  recurring / Visit · city) · Result (Completed / Missed / Cancelled) · Pay / reputation ("$117",
  "-6 reputation", "—").

**The company name.**
- `Game.company_name` (""), `Game.COMPANY_NAME_MAX` (24), `clean_company_name(text)` (trimmed,
  "" if not 1–24), `set_company_name(text)`, `suggested_company_name()` — "Maple Snow Removal", from
  the player's street (neutral, valid).
- The form: title "Name your company", one line "Your company's name, 1 to 24 characters.", a
  `LineEdit` (max 24, prefilled with the suggestion and selected, so typing replaces it; focus on
  open), OK (Enter too). An empty or blank name shows "Use 1 to 24 characters." and keeps the field.
  The sidebar's status line says "Company named: …" (no notification).
- Rename (Contracts) opens the same form with the current name and a Cancel button.
- Where the name shows: the header; Contracts; the board ("Bidding as …"); award notifications
  ("Bid accepted! Maple Snow Removal wins 16 Birch Avenue — one-time job."; unnamed: as before); the
  History tab (under the name); the map legend ("Contracts — <name>:", shrunk to fit its 440 px);
  the end-of-winter summary ("<name> — reputation: N / 100 · Balance: …"). The commercial property's
  sign is §16's.

**Input isolation.**
- `Game.typing()` — true while a `LineEdit` / `TextEdit` has the GUI focus.
- `game_root._unhandled_input` returns at once while typing (so E, M, V, 1–4, wheel, F1 and anything
  added there later — the fast-forward key — do nothing), and the Tab overview doesn't open.
- The computer was already a modal (player frozen, `input_captured()` false), so the foot / vehicle
  handlers and the polled tool keys never ran there; printable keys are eaten by the field.
- Found with a standalone probe (`probe/`): in Godot 4.7.2 Esc on a `LineEdit` ends *editing* but
  keeps the *focus*, and a focused field that isn't editing lets keys through to `_unhandled_input`.
  So `ComputerUI._input` takes Pause / `ui_cancel` while the field has focus and releases the focus
  ("Esc leaves the field"); the next Esc closes the computer as before. The field keeps editing
  after Enter (`keep_editing_on_text_submit`) and has no right-click menu (it would take the keys).
- The computer never rebuilds an app while the form is up or a text field has focus (the 2 s / 30 s
  refresh and the data signals used to rebuild under the player's hands).

**The monitor's desktop.** Same apps, same order (two columns, top to bottom), drawn from the ids;
taskbar pins Weather, Contracts, Contract board, Equipment store. The icons are 90 px wide (were
80; pitch 94) and each name's size shrinks (10 → 9 px) until it fits, with a dark shadow so the
names over the snowy hills read: before, "Property & Stor", "Equipment Stor" were cut off and "Bills
& Payments" was white on the snow (`before_monitor.jpg` / `after_monitor.jpg`).

## 7.2 Saves — version 3

- `Saves.SAVE_VERSION` 2 → **3**; `MIN_VERSION` stays 1. Migrations in order on load: 1 → 2
  (`_migrate_v1`, unchanged), 2 → 3 (`_migrate_v2`: an empty name and an empty history). The atomic
  write and the `.bak` are unchanged.
- New keys, both optional: `game.company_name` (string, default ""; an invalid saved name reads as
  "" so the form shows) and `contracts.job_history` (array, default []; entries cast on load,
  addresses re-read through `Layout.current_place`).
- The old `contracts.history` (completed one-time jobs, the pre-v3 list) is still kept, written
  and renamed on load as before (the §5 test reads it); the UI shows `job_history`. Old saves start
  with an empty history, as the brief says.
- History entries: `{id, address, client, type, result, time, year, pay, rep}`. Written by
  `Contracts.record_job(c, result, pay, rep)` from `_finish` (one-time job: completed, pay, +2; a
  recurring / city visit: completed, the visit's pay, +1 or +0.3), `_lose` (missed, 0,
  −`contract_lost_reputation`). "cancelled" is supported (shown as "Cancelled", "—") for §16; nothing
  cancels yet. Gerry's job is recorded too (it is a one-time job the player held).
- Cap: new balance value **`contract_history_max` = 200** (`data/balance.tres` and the default in
  `scripts/data/balance_data.gd`, "Contracts" group); the oldest entries go first.
- Tests: `test_s7_v2_save_loads_into_v3` (a pass-5 version-2 fixture → empty name and history, the
  old list kept, written back as version 3 with both keys; a version-1 file made from it — no boxes,
  no lock flag — goes 1 → 2 → 3 and plays) and `test_s7_v3_save_round_trips` (the name and four
  history entries of every kind and result, byte-identical as JSON after save → load). Every pass-3,
  pass-4 and pass-5 fixture loads into version 3 and plays (the fixture tests, below).

## 7.3 Fit and alignment — automated

`test_s7_every_app_fits` (headless, real font metrics): the game has no separate UI-scale setting —
the stretch mode (`canvas_items`, aspect `expand`, base 1920 × 1080) gives each resolution its UI
scale, so the four resolutions are their logical canvases, as in the pass-3/4 fit tests: 1280×720,
1920×1080, 2560×1440 → 1920 × 1080; 3440×1440 → 2580 × 1080. On each, a `ComputerUI` is laid out in
a host of that size, filled to the worst case (Survival with the power cut — the battery line —, a
24-character "WWW…" name, three contracts, history of every result, a pending bid, a 120-character
alert, two orders including the pickup-plow install line, a bill and transactions), and each of 11
views (the nine apps, Contracts → History, the name form) is checked at its top and scrolled to its
bottom: the window on screen at exactly 1640 × 900 (it grows if anything inside is too wide); every
visible control inside the window, and the content's inside the content area horizontally (it only
scrolls vertically); no unwrapped label or button whose text (measured with its font) is wider than
the control; no wrapped label with lines cut; the name field ≥ 300 px; every table column aligned;
a long app scrolls. 88 views, all pass. Tried the other way: a 900 px bid label (window grows to
1999 px) and a clipped header label (545 > 100 px) each fail it.

## Readings taken

- **Renames.** "Rename only where needed to match the list": the list's names are matched exactly,
  case included (so "Contract Board" → "Contract board" etc.), and "Property & Storage" follows the
  same case for consistency. "Active Contracts" → "Contracts" is the one real rename.
- **"The rest"** = Property & storage and Help, in their old relative order. There is no separate
  Map or Alerts app (the map is the M overlay; alerts are in Weather).
- **Weather first** needed no saved state: a new `ComputerUI` is built on every use and opens on
  Weather; nothing remembers the last app (so save → load can't change it).
- **The form's suggestion** is prefilled and selected (one key replaces it, OK accepts it) rather
  than a placeholder, so OK always has a valid name to take.
- **"Old saves start with an empty history"**: a new key, `job_history`; the pre-v3 `history` list
  (completed one-time jobs) is kept and still written but no longer shown. An old save's completed
  and lost contracts therefore no longer appear on the computer (Active now lists running contracts
  only); its running ones do.
- **Active's "due time"**: today's snowed-in time left, the only deadline that exists until §10.
- **Reputation**: the value only ("Reputation 52"); tiers and progress are §10's.
- **Award notifications** name the company only once it has a name (bids can't be placed before:
  the board asks first; F1's "Win first listing" sends no notification).
- **History entries per visit** for recurring and city contracts (each visit is a job paid on its
  own); Gerry's trail is recorded as a one-time job.
- **UI scale**: none exists; the four resolutions' logical canvases are what changes (above).
