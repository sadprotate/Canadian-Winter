## 13.1 What changed

**One table, built at load time** — `scripts/data/item_upgrades.gd` (`class_name ItemUpgrades`,
new). Reading taken: "`generate_data.gd` generates them" → the reading that changes the least is
*built at load time from one table*: no generator is recreated (AGENT_BRIEF: don't), no data file
is added, and the old `data/upgrades/*.tres` stay as the levels' templates, so "each level's effect
is what it is today" is literally the same value read from the same file.
- `TRACKS`: capacity (`shovel_capacity_1`, `_2`), throw (`throw_1`, `_2`), push width
  (`blade_width_1`), push power (`clear_speed_1`), intake (`blower_intake_1`), chute
  (`blower_throw_1`), front plow (`pickup_plow`), plow width (`vehicle_width_1`), plow power
  (`vehicle_speed_1`), blower (`vehicle_blower_1`), heated cab (one new level) — each with the stat the
  game reads, what it improves for the ladder (`QTY`), and a short text ("+25% load and fill speed").
- Which tracks an item gets comes from its data (the effects it used): a shovel-type tool (bare hands
  included) capacity, throw, push width, push power; the electric shovel throw, push width, push power
  (no upgrade ever touched its intake); a walk-behind blower intake and chute; the plain pickup the
  front plow; a plow vehicle plow width and plow power; a blower vehicle its blower; a vehicle without
  a cab (the ATV) a heated cab. The dump truck: none.
- `ItemUpgrades.build(Catalog)` (from `Catalog._ready`) makes one `UpgradeData` per item, track and
  level into `Catalog.upgrades`, id `"<item>:<track>:<level>"` (e.g. `small_shovel:capacity:1`), name
  "Small Snow Shovel: Capacity 1", the old upgrade's value, the scaled price, `requires` the level
  before; `UpgradeData` gains `item`, `track`, `level`.
- The levels live in `Game.upgrades` (the save key the global upgrades used) — **saves stay version 3
  with no new key**: the same dictionary, new ids.
- `Catalog.UPGRADE_IDS` keeps the six upgrades that aren't an item's (clothing ×2, weather ×2,
  furnace, tool rack); the twelve old ones move to `Catalog.LEGACY_UPGRADE_IDS` (still loaded: the
  templates, and the names of old orders and crates; `can_buy` → "No longer sold."). New
  `Catalog.upgrade_ids()` = every level (ladder order) + `UPGRADE_IDS`.

**Effects.** One lookup, `ItemUpgrades.mult(item_id, stat)` (the product of the item's owned levels
for that stat), replaces `Game.stat_value` in `ToolController` (`_capacity`, `_fill_rate`,
`_throw_dist`, `_push_half_width`, `_push_strength`, the two push speeds — `data.id`), `WalkBehind`
(intake, chute) and `Vehicle` (plow width, plow power, blower ×2). `Game.stat_value` now skips item
levels (it serves clothing, the furnace and the weather apps, unchanged).

**Prices** scale with the item's price: a level costs its old upgrade's price × the item's price ÷ its
family's reference price, to two significant figures (`ItemUpgrades.nice_price`, at least $1):
hand tools and the electric shovel $400 (so the small shovel's every level for sale costs about the
shovel, $26 for $25), walk-behind blowers $790 (the small blower pays today's prices), vehicles
$14,000 (the tractor with blade pays today's prices); bare hands count as a $12 item. The front plow
keeps its $3,400 (the pickup has no price). The heated cab: `upgrade_cab_price` $1,500 at the vehicle
reference → the ATV's $700. Every price is in the 13.3 table.

**Ownership.** `ItemUpgrades.owns(item)`: bare hands always; a tool or machine in a slot, in your arms,
on the rack, lying anywhere (the buried opening shovel too), at the store's pad, or on order; a
vehicle you have or have on order. Levels belong to the type, so a dropped, racked or second copy
of a tool reads the same levels. `Economy.can_buy` for an item's level: "Buy the Large Snow Scraper
first." / "Fit the front plow first." (the plowed pickup's tracks) / "You need your pickup truck."
(the plow) / "Requires level 1." / "Fully upgraded." (past the ladder) / "Survival Mode only."
(the cab in Fun Mode) / "Already owned." (owned or on order).

**The plow bug.** The front plow is the pickup's upgrade, id `ItemUpgrades.PLOW_ID`
(`pickup:front_plow:1`), no longer a vehicle id, so `item_kind` says "upgrade": it is ordered once,
no truck is delivered, it can't be bought again, and it is still fitted when the pickup drives into
the store lot (`Store` reads the new id; the Orders app's "Drive your pickup into the store lot…"
too). `Economy.can_buy` also refuses any vehicle the store doesn't sell ("Not sold in the store."),
so `buy("pickup_plow")` can't deliver a truck any more. Old orders with item `pickup_plow` (sold as
vehicles) become the plow's upgrade order on load (`Economy.deserialize`): a pending or ready one
delivers the plow, never a truck.

**The heated cab** (§14 owns its warmth). The ATV (the only vehicle without a cab) has a "Heated cab"
track: bought and collected like any vehicle upgrade, sold in Survival only (Decision 9: cab heat
doesn't matter in Fun Mode, so Fun Mode doesn't show it). The flag per vehicle type is
`ItemUpgrades.has_heated_cab(vehicle_id)` (built in: `VehicleData.heated_cabin`; or bought). Not
wired: `Vehicle` still reads `data.heated_cabin` for its heat; a comment at that line points to the
hook.

**The Upgrades app** (`ComputerUI._upgrades`), grouped by item, owned first:
- one line ("Each item has its own upgrades. Crates wait on the store's pickup pad; apps and home
  services start right away.");
- **Your items**: a card per owned item in the ladder's order, with the item's own icon (`Icons.tool`;
  the mitten for bare hands; vehicles have no icon in the set — a 72 px gap keeps the columns in line)
  and a row per track: name, "Level 1 / 2", the next level's effect (or "Fully upgraded" / "Fitted"),
  its price, Buy (the reason under it: "Not enough money.", "On order.", "Fit the front plow first.").
  The pickup and the plowed pickup are one card (one truck). A level carried over past the ladder
  shows as the top ("Level 2 / 2");
- **Other items**: one table row per item you don't own — its tracks and where to get it
  ("Equipment store · $265", "Fit the pickup's front plow first");
- Cold protection, Weather technology, Property: the old cards (`_store_card`), unchanged.
- `ComputerUI.upgrade_groups()`, `_group_owned`, `_upgrade_item_card`, `_upgrade_row`,
  `_item_icon`, `_icon_id`; `_upgrade_icon(u)` (§6's hook) now returns the item's own icon id.
  Cards carry meta `upgrade_item` (a rebuild in the same frame renames nodes).
- The Property app's "Upgrades owned" is a table per item ("Small Snow Shovel · Capacity 1, Throw 1",
  then "Other"); the Tab panel's line is the tool in your hands: "Upgrades — Small Snow Shovel:
  Capacity 1" (+ clothing).

**Presses and keys.** Buy is a computer click (UI clicks aren't capped, §2); the world-changing press
— collecting a crate at the store — is Interact (E), already through `Settings.accept_press`. No key
is named in any new text; the plow's fitted notification keeps its `action_label` keys.

## 13.2 The ladder

**How it is read.** At base, the items keep HANDOFF §7's order: `ItemUpgrades.ladder()` is
`Catalog.TOOL_IDS` (bare hands, small shovel, standard shovel, wide pusher, scraper, large scraper,
sleigh, electric shovel, small blower, large blower — tier and price rise along it) then
`Catalog.VEHICLE_IDS`; no base value changes. A single "power" number across a shovel, a pusher and a
blower would be made up, so the ladder is checked **per thing a track improves** (`QTY`: load,
fill speed, throw, push width, push strength, intake), against **the next item in the ladder that
has it**: a track's levels for sale stop where the item's value would pass the next item's base by
more than `upgrade_ladder_slack` (**15 %**) — unless the item is already ahead there at base (the next
item is another kind of tool: the standard shovel out-throws the wide pusher, the pusher out-pushes
the scraper). With today's effects that trims five levels: the small shovel's capacity 2 and throw 2,
the wide pusher's capacity 2 and throw 2, the scraper's throw 2. Every other track keeps all of today's
levels. Old saves keep those five levels if they had them (Decision 8, 13.4).

## 13.4 Old saves

Saves stay **version 3**, no new key: the levels are new ids in `game.upgrades`. On load
(`Game.deserialize` → `ItemUpgrades.migrate`) every old global level in the list goes to **every
item it used to affect, owned or not** — the item types of the tracks it was the level of, levels
1…n (e.g. `throw_2` → throw 1 and 2 on bare hands, the six shovel-type tools and the electric
shovel) — even past an item's ladder (the small shovel keeps capacity 2 if it had it: nothing paid for
is lost) — and leaves the list; the upgrades that aren't an item's stay as they were; `pickup_plow` →
the pickup's front plow. One notification once the game is up (`ItemUpgrades.pending_note`, pushed by
`game_root._ready`): "Upgrades now belong to each item. Everything you bought carries over to every
item it improved." It is idempotent: the save written afterwards has no old id, so no second note.
An old order's crate collected later (`Game.grant_upgrade` of an old id) carries over the same way.
Each item's effects are exactly what the global upgrades gave it (tested against the old rule).

**The `2_upgrades` fixture** (both modes; every old upgrade bought, so 18 → 69 entries) loads, every
item gets its levels, one notification, sleep → autosave → reload with the same levels and no
note. **Its extra truck** (the bug's second pickup-with-plow, delivered to a store bay at 40, 96.6)
**is kept where it is**: it was delivered, and an old save loses nothing; both plowed pickups share
the plowed pickup's upgrades. Its order (#7, kind "vehicle", collected) becomes the plow's upgrade order
(kind "upgrade", collected); nothing new is delivered; the plow isn't for sale again. Reading: the
reading that changes the least (removing a truck the player may have used would take something away).

## 13.5 `EQUIP_RATE` (the board's listing size cap) — decided: not fed by upgrades

`Contracts.res_cap_m3()` scales the residential size cap by `EQUIP_RATE[equipment_capability()]`, a
class table (hand tools / pushers and the like / walk-behind blowers / plow or blower vehicles) of
what the player owns. Upgrades don't feed it: the ladder keeps a fully upgraded item at about the next
item's base, mostly inside the same class (the standard shovel's full upgrade improves its scooping,
not its pushing, so it isn't a pusher-class tool), and the cap's calibration (18 m³ = a typical
driveway after a storm with a small shovel, §10a) doesn't model per-level gains. The table and
`equipment_capability()` are unchanged. §13b's equipment entries are noted below.
